Por que rodar local?

💰

Custo

APIs pagas cobram por token. Projetos de uso intensivo ou contínuo tornam-se proibitivos em pouco tempo.

🔒

Privacidade

Logs de sistema, saídas de produção e dados sensíveis não devem sair da sua infraestrutura.

📡

Dependência

Sem internet, sem modelo. Ambientes air-gapped, edge computing e CI/CD offline ficam impossíveis.

"E se o modelo rodasse na sua máquina, como um daemon do sistema?"

A premissa: o modelo fica onde os dados estão.
03 / 22

O que é o Ollama?

  • Runtime open-source para LLMs — instala como um serviço do sistema
  • Empacota modelos em formato GGUF com um servidor HTTP local na porta 11434
  • API REST compatível com OpenAI — qualquer SDK existente funciona
  • Suporte nativo a GPU (CUDA e Metal) com fallback automático para CPU
  • Modelfile: arquivo declarativo para criar modelos customizados (persona, temperatura, janela de contexto)
# os 5 comandos essenciais
ollama pull qwen2.5-coder:1.5b
ollama run llama3.2
ollama list
ollama serve
ollama create alde -f Modelfile
Ollama é para modelos o que o Docker é para containers.

Por que Ollama e não uma API paga?

Critério API OpenAI / Claude Ollama local
Custo por requisição US$ 0,002–0,06 / 1k tok US$ 0,00
1.000 req/dia (mês) US$ 60–1.800 / mês custo de luz
Logs de 32k tokens US$ 0,48–0,80 por análise US$ 0,00
Privacidade dos dados termos permitem uso 100% local
Funciona offline não sim
Rate limit sim — para em pico não existe
Setup conta + cartão + chave API um comando de terminal
Controle do modelo nenhum total (Modelfile)

Para projetos acadêmicos ou protótipos com uso contínuo, Ollama elimina o custo de inferência completamente. O único custo é a máquina que você já tem.

Quando faz sentido usar API paga: modelos frontier de última geração (GPT-4o, Claude Opus 4), produção com SLA crítico, ou quando não há hardware disponível.

Custo zero de inferência é uma vantagem estrutural — não temporária.

Do zero ao modelo rodando em 3 comandos

instalar
curl -fsSL https://ollama.com/install.sh | sh

Instala o Ollama como serviço do sistema. Funciona em Linux, macOS e Windows (WSL). Após isso: ollama serve já está rodando em background.

baixar modelo
ollama pull qwen2.5-coder:1.5b

Baixa ~1 GB. Armazenado em ~/.ollama. Roda em qualquer máquina com 4 GB de RAM. Só baixa uma vez — execuções seguintes são instantâneas.

testar no terminal
ollama run qwen2.5-coder:1.5b

Chat interativo direto no terminal. Ctrl+D para sair. Sem interface, sem login, sem internet.

chamar via API
curl http://localhost:11434/api/generate \
  -d '{"model":"qwen2.5-coder:1.5b","prompt":"...","stream":false}'

A API já está no ar desde o passo 1. Compatível com o formato OpenAI — sem mudar SDKs.

criar customizado
ollama create alde -f Modelfile
ollama run alde

Modelo com persona, temperatura e system prompt definidos pelo desenvolvedor — é o que o ALDE usa.

Cada etapa acima é exatamente o que o projeto ALDE executa no docker-compose.

FROM qwen2.5-coder:1.5b

PARAMETER temperature 0.2
PARAMETER top_p 0.85
PARAMETER top_k 40
PARAMETER repeat_penalty 1.1
PARAMETER num_ctx 32768
PARAMETER num_predict -1
PARAMETER stop "<|im_end|>"
PARAMETER stop "<|endoftext|>"

SYSTEM """
Você é o ALDE (Assistente Linux de Diagnóstico e
Execução), um engenheiro DevOps sênior especializado em:
 • Diagnóstico de hardware e drivers em Debian/Ubuntu
 • Containers Docker e orquestração com docker-compose
 • Análise forense de logs (journalctl, dmesg, syslog)
 • Automação via shell scripts (Bash/POSIX sh)
 ... (regras de segurança, formato de saída, etc.)
"""

→ FROM: modelo base (qualquer modelo do Ollama Hub ou HuggingFace)

→ PARAMETER: ajusta comportamento de geração sem recompilação

→ SYSTEM: define a persona e as regras do assistente

Um Modelfile é um Dockerfile para a mente do modelo.

MODELO

Modelfile — É a "receita" do assistente: define o modelo base (qwen2.5-coder:1.5b), temperatura 0.2 para respostas determinísticas, contexto de 32k tokens e o system prompt completo com regras de comportamento do ALDE. Criado com: ollama create alde -f Modelfile

INFRAESTRUTURA

docker-compose.yml — Orquestra tudo em sequência: (1) Ollama sobe e passa o healthcheck, (2) setup baixa o modelo e cria a persona, (3) API FastAPI sobe e espera o setup completar. Um único docker compose up -d faz tudo.

RAG LEVE

knowledge_base/retrieval.py — Sem embeddings, sem banco vetorial. A query do usuário é tokenizada, cada comando do JSON recebe um score de sobreposição, os top-6 entram no system prompt. Leve, rápido e funciona offline junto com o Ollama.

API

app/services/ollama_service.py — Faz as chamadas ao Ollama via httpx assíncrono. Resolve o modelo disponível em runtime (fallback automático), monta as opções por perfil e suporta tanto geração batch quanto streaming SSE.

Nenhuma dependência externa — tudo roda na mesma rede Docker interna.

RAG sem banco vetorial — como funciona

01
query do usuário
"como ver portas abertas?"
↓
02
tokenização
tokens: {"ver", "portas", "abertas"} — stopwords removidas, mínimo 3 chars
↓
03
scoring contra knowledge_base.json
ss -tulpn → score 4 (match em cmd + desc)
lsof -i :<PORT> → score 3
ss -s → score 2
↓
04
top-6 injetados no system prompt
"Comandos relevantes da base de conhecimento: • ss -tulpn — Portas em escuta com processo..."
def _score(entry, query_tokens):
    cmd_tokens = _tokenize(entry["cmd"])
    desc_tokens = _tokenize(entry["desc"])
    # match no cmd vale 2x mais que na desc
    return (
        len(query_tokens & cmd_tokens) * 2 +
        len(query_tokens & desc_tokens) * 1
    )

def retrieve(query, top_n=6):
    query_tokens = _tokenize(query)
    scored = [
        (entry, _score(entry, query_tokens))
        for entry in _load_entries()
    ]
    top = sorted(scored, key=lambda x: x[1],
                 reverse=True)[:top_n]
    # filtra score mínimo 2 para reduzir ruído
    return [e for e, s in top if s >= 2]

Por que não embeddings? Para contextos estruturados com vocabulário técnico previsível (comandos Linux, flags Docker), sobreposição de tokens é suficiente e elimina a dependência de modelos de embedding, GPU e banco vetorial — tudo roda offline.

O JSON é carregado uma vez via lru_cache — zero overhead por requisição.

Do input ao output — anatomia de uma chamada

01 Usuário envia mensagem — frontend ou curl
02 ChatRequest validado pelo Pydantic
03 KB Retrieval: query tokenizada, top-6 comandos selecionados por score
04 System prompt montado: SESSION_PREFIX + KB context · perfil define a temperatura nas options
05 Ollama resolve modelo disponível: alde → qwen2.5-coder:1.5b → qwen3-coder-next
06 POST para /api/generate ou /api/chat (Ollama local)
07 Resposta retornada como JSON ou stream SSE
08 Histórico da sessão atualizado em memória
Cada requisição constrói o prompt do zero — contexto explícito, não implícito.

Pipeline de Qualidade e CI/CD

  • ruff check . — lint e regras de qualidade

  • Cobre: routes, services, KB retrieval, helpers
  • Mocks para Ollama e KB — sem dependências externas
→
03

docker-build

  • Build da imagem com cache GHA (layers cacheadas entre runs)
  • python:3.11-slim, usuário non-root (alde)
  • Healthcheck nativo via curl /health · push: false
# .github/workflows/ci-cd.yml — trecho
jobs:
  lint:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.11", cache: "pip" }
      - run: pip install -r requirements-dev.txt
      - run: ruff check .
      - run: ruff format --check .
      - run: mypy app/

  test:
    needs: lint
    steps:
      - run: pip install -r requirements-dev.txt
      - run: pytest

  docker-build:
    needs: test
    steps:
      - uses: docker/setup-buildx-action@v3
      - uses: docker/build-push-action@v6
        with: { push: false, cache-from: type=gha }

✓ Lint — Código limpo antes de qualquer merge. Zero warnings tolerados.

✓ Test — Mocks isolam o Ollama — o modelo não é testado, só a API e os serviços. CI roda sem LLM instalado.

✓ Build — Valida que o Dockerfile builda sem erros. Imagem single-stage (python:3.11-slim), layer cache via GHA, non-root por padrão. Nunca faz push para registry.

Gatilhos automáticos via GitHub Actions: push em main · feat/** · fix/** e pull requests para main

CI/CD é o que separa um experimento de um projeto.

Ollama além da API — ferramentas CLI

oterm

TUI (interface de terminal) para o Ollama. Múltiplos chats, histórico persistente, troca de modelo sem sair do terminal.

Uso: pip install oterm && oterm

shell-gpt

Integra LLM diretamente ao shell. Gera e executa comandos, explica erros, cria scripts automaticamente.

Uso: sgpt "como matar processo na porta 8080" --shell

aichat

Cliente CLI multi-provider (Ollama, OpenAI, Gemini, Claude). Suporte a RAG, agentes e execução de código.

Uso: aichat -m ollama:qwen2.5-coder "explique este erro"

llm

CLI minimalista com plugin llm-ollama. Histórico em SQLite, templates, piping de stdin — composível com qualquer ferramenta Unix.

Uso: cat error.log | llm -m ollama/alde "o que causou isso?"

fabric

Framework de prompts pré-construídos (patterns) para terminal. Compatível com Ollama. Mais de 200 patterns prontos.

Uso: cat artigo.txt | fabric --pattern summarize

O terminal é sua IDE — o LLM é seu co-piloto.

Encontrando e importando modelos

Hugging Face + GGUF

  • GGUF = formato de quantização para CPU/GPU consumer
  • Filtro: huggingface.co → Models → GGUF → Text Generation
  • Quantizações: Q2_K (menor) → Q8_0 (maior). Recomendado: Q4_K_M
  • Importar direto: ollama run hf.co/bartowski/Llama-3.2-3B-Instruct-GGUF
  • Ou via Modelfile: FROM hf.co/...

OpenRouter na prática

  • 200+ modelos via API unificada
  • Troque APENAS a base_url:
    base_url = "https://openrouter.ai/api/v1"
  • Modelos gratuitos:
    mistralai/mistral-7b-instruct:free
    meta-llama/llama-3.2-3b-instruct:free
    google/gemma-2-9b-it:free

Regra prática de RAM: 1.5B → 2-3 GB · 7B → 5-8 GB · 13B → 8-12 GB · 70B → 40+ GB. Quantização Q4 reduz ~60% o consumo com perda mínima de qualidade.

GGUF democratizou os LLMs — roda em qualquer notebook.

Além do Ollama — outras opções

LM Studio

Interface gráfica (Windows/Mac/Linux) para baixar e testar modelos GGUF. Servidor local compatível com API OpenAI. Ideal para quem prefere GUI ao terminal.

llama.cpp

O motor por baixo de quase tudo (Ollama usa internamente). Inferência em C++ pura, zero dependências, máximo controle. Referência para pesquisa e benchmarking.

LocalAI

Drop-in replacement da API OpenAI para uso local. Suporta LLMs, imagens (Stable Diffusion) e áudio. Mais complexo.

vLLM

Otimizado para throughput em GPU — ideal para servir modelos em produção com múltiplos usuários simultâneos. Foco em escala, não em uso pessoal.

Jan

App desktop open-source similar ao LM Studio. Servidor local incluído, forte foco em privacidade.

GPT4All

App desktop simples, foco em acessibilidade para usuários não-técnicos. Modelos curados e otimizados pela equipe.

Ollama vence em: simplicidade de instalação · integração DevOps · ecossistema CLI · velocidade de setup

Escolha pela necessidade: pesquisa→llama.cpp · produção→vLLM · uso pessoal→Ollama.
